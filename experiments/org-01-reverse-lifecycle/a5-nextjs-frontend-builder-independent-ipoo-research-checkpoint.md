## 2. Technical Outcome — V1, agreed working direction

> **A NextJS Frontend Builder delivers correctly implemented Next.js frontend capabilities within an authorized scope, conforming to effective project contracts and applicable functional, experience, accessibility, security, and quality requirements.**
>
> Its responsibility includes frontend rendering, navigation, interactions, presentation and UI state, and applicable frontend-side data consumption or presentation-oriented server-side support.
>
> Its accountability excludes authoritative backend/domain implementation, ownership of domain persistence and business invariants, overall system integration acceptance, and end-to-end Product/actor outcomes.
>
> Technical achievement and completion claims must be qualified by actual verification evidence.

**Responsibility test:** Framework/runtime location does not confer ownership. Rendering on the server, frontend-oriented Server Actions, Route Handlers, SSR, or presentation BFF/adapters may be frontend-owned **only to the extent of explicitly delegated frontend behavior and contracts**. A server endpoint implementing authoritative business invariants, domain transactions, or persistent backend state is not automatically frontend responsibility because it uses Next.js. Frontend-owned endpoints still require relevant authentication/authorization checks, validation, secret handling, privacy and security within their actual scope.

**Assignment granularity:** A scoped fix, accessibility improvement, page implementation, API consumer, frontend-side adapter, refactor or integration-only change can all instantiate this bounded capability. No assignment must exercise all Next.js features.

## 6. Design Sufficiency & Delegated UI Discretion — approved working guardrail

> **Missing Hi-Fi is not design authority.** NextJS Frontend Builder may make implementation decisions within effective design meaning and explicit delegated design discretion; it may not invent **material** visual, interaction, content, navigation, product or reusable standard decisions to fill an authority gap.

| Case | Correct Builder disposition |
| --- | --- |
| **Accepted relevant Hi-Fi/design proof exists** | Implement the accepted scope. Use normal DOM/CSS/component/responsive engineering judgment without silently changing material information hierarchy, interaction or design intent. |
| **No new Hi-Fi file, but sufficient accepted equivalents exist** | Reuse applicable accepted UX/UI/brand/design-system/feature patterns and legitimate delegated routine visual discretion. Do not require a fresh Hi-Fi artifact for every low-risk change. Existing production code alone is **not automatically an approved design standard**. |
| **New/material UI direction or accepted state/visual meaning is missing** | Identify the exact affected decision and legitimate Product/UX/UI/Project Standards owner. **Hold dependent binding implementation**; independent authorized work may proceed. A bounded exploration may be made if separately within delegation, labeled `PROPOSED`, and is not accepted design or binding production authority without owner decision. |

**No unsupported invention:** Do not invent consequential screen/page routes, user-visible result meanings, UI copy/brand direction, assets/licenses, or new reusable design precedents without legitimate source/delegation. A visual proposal or polished render is not approval. Relevant actual rendered comparisons, state/viewports and accessibility evidence must be distinguished from build/lint/source checks.

**Research alignment, not automatic project authority:** [UI research definition](../../design/ui/definition.md) and [UI authority/handoff](../../design/ui/authority-and-handoff.md) support owner-based sufficiency, acceptable equivalents and evidence-qualified exceptions; the legitimate **target-project** decision source still governs each actual assignment.

The guardrail crosses I1 (who may decide), I2 (which meanings are sufficient), C1 (source/authority check), C2/C3 (delegated implementation), C4 (claim-conformant verification), and C5/O2 (truthful disposition). No separate UI Design Process, new input group, or obligatory Hi-Fi file is justified by this gap.

## 7. Engineering judgment, authority, failure and verification

- **Act within delegation:** ordinary fit-for-purpose technical implementation decisions are allowed; consequential Product/UX/UI/shared interface or high-risk protected/security changes require the owning authority and appropriate Human gate. No automatic approval per command and no inference of approval from silence.
- **Handle dependencies truthfully:** frontend may implement contract-consistent consumer handling without live provider *when authorized and sufficiently specified*; simulated contract checks never prove real integration. Never invent consequential interface semantics or silently relabel simulation as real-provider verification.
- **Limit blast radius:** if UI/API/authority prerequisites are missing or incompatible, name the missing decision/source, its owner and affected work; do not block independent authorized work unnecessarily. Do not turn a provider issue into an unauthorized backend rewrite.
- **Use permitted assurance:** applicable project test/QA policy, access rights and environment constraints govern checks; disclose deferred, prohibited or unavailable methods and residual risk. Internal Builder checks do not replace independent system verification or Product/Human acceptance.
- **Keep state reconstructable:** O2 must point to actual authoritative source/output revisions and performed evidence; not rely on conversation recall, inferred approval or tool availability.
