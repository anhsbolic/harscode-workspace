## 3. Minimal prospective R4 evidence procedure (trial-only)

The facilitator is responsible for keeping the following source/input boundary inspectable. **This is a light experiment protocol, not a new Harscode stage, mandatory registry, state machine or reusable Space policy.**

**Before consumer execution:**

1. Choose a **regular persistent chat outside the Harscode Project**, not Temporary Chat, where the full transcript can be retained. Disclose known Memory/Project/global custom-instruction influences; if verified clean context is unavailable, report isolation as **UNVERIFIED**, not independent PASS. Do not place upstream evaluation or R3 expected answers in the consumer context.
2. Freeze a **single exact input manifest**: scenario fixture, role-specific contract exact revision, original U and I outputs (when consuming downstream), all relevant original owning sources, and explicit standing/approval limits. Use attachment filenames + content SHA-256 or immutable Git blob/commit; distinguish `INPUT SUPPLIED`, `POINTER ONLY`, and `INTENTIONALLY WITHHELD`.
3. Explicitly **supply original Product fixture as its own source**, not merely say it exists within an upstream report. Supply **full, unaltered U output** for UI; for Engineering supply full unaltered U + I and original fixture + Rancang contract. The next experimental consumer does not inherit any presumed chat/source history.
4. **At the beginning of the trial, before substantive analysis, request a consumer-generated input receipt** stating each actual file name, fingerprint (only if computed), readable/unreadable status, source scope and mismatches. Do not claim unseen paths are accessible. Acknowledge missing material immediately and mark dependent tasks blocked/conditional as appropriate.

**After consumer execution:**

5. Preserve the actual prompt, input manifest, consumer receipt, final complete response, generated source artifacts and their exact hashes/screenshots if produced, and a small dated evidence note referencing the full saved transcript. **Do not save only the executive summary.** User-controlled durable attachments or a research evidence artifact suffice; choose the simplest available path.
6. Compare **intended -> delivered -> readable -> actually inspected**, keeping observed facts separate from consumer self-report and unavailable tool traces. Do not assert upload failure solely because a consumer reports a file missing. Keep source-level content acceptance distinct from approval, security assurance, user evidence, and runtime verification.
7. A new run may test **prospective semantic consumer fit**. It **cannot** reverse-engineer I1's missing Temporary Chat trace. Keep I1 historical attribution closed unless materially new primary historical evidence becomes available.

**One compact receipt line per source is sufficient:** `source name | supplied route (attachment/paste/immutable link) | expected fingerprint | observed fingerprint or NOT CHECKED | readable status | consumer inspection status | standing/limit`. No extra tooling or workflow automation is required by this procedure.
