# UX AGENTS — Direct Concern Instructions

> **Standing:** PROPOSED A2 RESEARCH GUIDANCE; not project UX authority or permission to write, invoke, test, deploy or promote.

## Required behavior for UX assignments

1. Start at [UX README](README.md), then use [UX Definition](definition.md) and [UX Authority & Handoff](authority-and-handoff.md) as applicable. Do **not** depend on a parent `design/AGENTS.md` or an unnamed UI/Project Standard agent to understand UX responsibilities.
2. Identify the **actual decision** and relevant actor/domain consequence. Inspect current **target-project owning Product/UX/Design Standard sources and exact approved revisions**, applicable accessibility/device, privacy/security and relevant technical constraints directly. Preserve source/provenance and label working hypotheses versus accepted meaning.
3. Bounded exploration may proceed on explicitly hypothetical Product inputs; **binding consequential UX decisions** require the relevant Product authority. Ask its legitimate owner for missing material Product meaning rather than fabricating it.
4. Choose proportionate UX work: actor scenario, UX Flow, IA, navigation, webpage map if web-routing is material, structural wireframe, interaction states, bounded prototype, evaluation and decision review. These are **not mandatory stages**.
5. Protect truthful Product claims, status/provenance, required pre-effect comprehension, negative/incomplete/uncertain results, keyboard/focus/screen-reader use and responsive information priority. A response timeout cannot be called a confirmed Product failure or success without evidence.
6. Challenge UX trade-offs, make one grounded recommendation when direction is clear, and record actual evidence limitations. Material Human acceptance must point to exact reviewed UX meaning/revision and scope in the owning project.
7. Handoff **required information** directly to receiving responsibilities; do not dispatch a named Space or treat a prototype/screenshot as an approval. Return Product gaps to Product owner, UX gaps to UX owner, reusable-rule changes to Project Standard owner, technical questions to Engineering authority.
8. For a new bounded UX output artifact, the optional [UX Output authoring template](templates/ux-output.id.md) standardizes information and handoff headings. Use an existing sufficient project-owned format when applicable; do not require nine files or treat completed fields as approval.

## Never

- Invent roles, eligibility, consent/legal status, privacy requirements, financial effects, product success, business rules or backend behavior.
- Impose UI visual styling, Design System changes, APIs, schemas, code architecture or router implementation as UX-owned policy.
- Promote a one-off interaction/prototype to reusable Project Design Standard automatically.
- Assume Lo-Fi is always required before Hi-Fi or Engineering; assume all experiences have webpage routes.
- Claim usability, accessibility certification, integrated runtime or real-user evidence based only on simulated clicks, mockups, Human aesthetic approval or source review.
- Treat available tools/formed Spaces as permission for protected actions.

**Ancestor rule:** the project/repository root `AGENTS.md`, actual project standards and harness-level security/authorization still apply. Concern independence is not a bypass of higher-level safeguards.
