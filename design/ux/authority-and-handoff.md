# UX Authority & Consumer Handoff

> **Standing:** A2 DRAFT / RESEARCH-ONLY; not target-project UX authority, Space authorization, or approved Project Design Standard.
> **Owner:** UX Interaction & Experience responsibility. Actual accepted project decisions belong to target project's legitimate owner at exact effective revisions.
> **Entry:** [UX README](README.md) · [UX Definition](definition.md).

## 1. Legitimate UX decisions

UX authority follows **meaning, owning project, authorized decision owner, scope and exact accepted revision**, not who drew the flow, authored a prototype or generated a file.

Distinguish **observed evidence**, **exploratory hypothesis**, **proposed UX decision**, **Human-accepted exact UX decision**, **currently effective UX source**, **superseded** and **unresolved/unknown**. They are semantic standings, not mandatory runtime workflow states.

Human approval should identify the actual interaction/IA/navigation/state question, inspected exact artifact and scope, applicable Product meaning, evidence/limitations, affected people/consumers, decision and unresolved questions. New material accepted UX precedent requires appropriate owner approval; routine delegated reversible choices need no blanket ceremony.

**Approval record and reviewed artifact can be separate.** Do not edit accepted UX content only to insert its own SHA/APPROVED metadata and then claim the prior approval covers different bytes. If approval precedes persistence, retain an immutable reviewed snapshot and verify the persisted content. Conversation-only assent without project-owned persistence is a working decision, not durable project authority.

## 2. What UX owns and cannot approve

UX owns bounded accepted interaction flows, IA, navigation/route decisions when applicable, user-facing interaction-state requirements and UX evidence. It cannot change accepted Product actor/domain rules, required disclosures, irreversible effects, legal/security/privacy claims, or Product success/failure semantics.

UX authority is separate from final UI visual expression, reusable Project Design Standard authority and Engineering architecture. A feature UX pattern **may be proposed** for reuse; it is not an approved project-wide standard unless the legitimate project-standard owner accepts that change at its exact revision.

Applicable repository root and project/Harness security and protected-write rules remain in force without any parent `design/AGENTS.md`.

## 3. Functional consumer interface

| Receiving responsibility | Applicable UX information needed |
| --- | --- |
| **Visual Interface & Content Design** | Accepted interaction progression, IA/content priority, navigation, web routes/page-vs-state if applicable, UX interaction states, accessibility and source standing |
| **Engineering Solution Design** | Material user interaction decisions, route/entry/exit meaning where applicable, pre-effect comprehension, failure/unknown/recovery behavior |
| **Engineering Development** | Applicable accepted UX obligations **plus separately owned** Product, UI, security, API/technical and codebase sources |
| **UX Verification & Acceptance** | Scoped accepted UX claims, representative branches/states, criteria, test evidence and actual limits |
| **Project Design Standard Definition** | Candidate recurring patterns, justified generality, affected standards and legitimate promotion authority |
| **UX Decision & Reconciliation** | Material conflicts/new findings, exact affected approved UX source, impact and right decision owner |

Consumers are **functional responsibilities**, never mandatory named Spaces or prior completed phases. Multiple subjects may satisfy a responsibility with legitimate assignment. Use existing accepted project source references directly rather than a second mandatory master UX Contract.

## 4. Minimum consumable information

For an actual receiving decision, the handoff must make discoverable:
- **Scenario and scope:** actor, goal, relevant Product constraints and what is excluded.
- **Accepted UX meaning:** flows, IA, navigation, interaction states, relevant responsive/accessibility obligations.
- **Web route contract if applicable:** accepted vs proposed paths, page purpose, entry/exit, page-vs-state decisions.
- **Effective source:** exact owning project revision, approval standing, legitimate Human decision, applicable standards.
- **Evidence and limits:** walkthrough vs prototype/simulation vs independent user/accessibility check vs actual implemented result.
- **Delegated freedom and material gaps:** what receiver can decide; missing information, affected blocked edge and authorized owner.

A short durable pointer to original project sources can be sufficient. **No nine-file UX packet or stage-based dispatch.**

## 5. Compatibility, contradictions, revision

**Generic fit:** if a relevant reusable receiving Input Contract actually exists, check semantics/completeness/standing against it; otherwise `NOT APPLICABLE`. **Project-bound fit:** check actual receiving project objective, security/accessibility constraints, accepted source revisions, action authorization and real evidence regardless of generic fit. If untested, report `UNVERIFIED`, never infer readiness from document existence.

Product gaps go to legitimate Product owner; UX route/IA conflicts to UX owner; reusable standards to project-standard owner; technical mechanism/feasibility to Engineering owner. A new finding never automatically amends accepted authority; independent authorized work can continue when its decision is not blocked.

Material UX semantic changes require scoped new effective approval and affected consumer check. Technical infeasibility can trigger revision, but does not transfer web navigation authority to backend API design. Preserve previous accepted bytes in Git; no competing history index in active UX guidance.

A clickable prototype is limited UX design evidence, not proof of real Product mutation, user comprehension, accessibility certification or Engineering verification. UX acceptance doesn't authorize UI implementation, protected writes, Space invocation, production or release.

**Final rule:** accepted UX decisions bind **their own scope and revision**; consumers depend on required information, not the identity of a producer.
