## UX responsibility

UX determines how a person **discovers, understands, navigates, acts, and recovers** while preserving Product meaning. It owns scenario-specific UX Journey, UX Flow, Information Architecture, navigation/webpage path decisions where applicable, structural layout/proofs, user-facing interaction/state requirements and scoped UX acceptance.

Product owns meaningful domain journey, authority and consequential information/rules. Visual Interface Design owns final expressive UI. Project Design Standards responsibility owns reusable rules **across outcomes**. Engineering owns technical mechanisms/implementation. UX may be consumed by each without requiring a mandatory sequence.

**Lo-Fi is a fidelity/proof method, not a mandatory lifecycle stage or new Harscode Space.** Nine logical UX outputs do not imply nine files or one prototype per assignment. Only relevant information must be sufficient for the real decision.

## Standing boundaries

Exploratory UX may use clearly marked Product hypotheses. A binding UX choice that depends on consequential Product meaning requires effective project authority for that meaning. Material UX approval is exact-revision and scope-bound; an accepted UX design is **not** Product policy, Design Standard promotion, final UI approval, actual usability proof or runtime verification.

Root `design/` instructions are not part of this concern's routing; repository-root and target-project security/authorization instructions still apply. Root Design exploration/authority documents remain transitional A3 research inputs, not extra UX instruction.
