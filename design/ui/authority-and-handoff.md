# UI Authority & Consumer Handoff

> **Standing:** A3 DRAFT / HUMAN CONTENT REVIEW PENDING (2026-11-04). Not an effective target-project UI contract, approved project-wide Design Standard, formed Space, Engineering implementation authorization or runtime acceptance.
> **Responsibility:** Visual Interface & Content Definition. Real project UI decisions are owned by the legitimate target-project Human/Design authority, with exact effective revision and scope.
> **Direct local entry:** [UI README](README.md) · [UI Definition](definition.md) · [UI AGENTS](AGENTS.md).

## 1. UI decision standing and authority

Approval follows **an identified design decision and exact reviewed artifact revision**, actual project owner/delegation, affected surfaces/states, supporting evidence and exclusions. Distinguish observed render/reference, exploratory candidate, proposed decision, scoped Human-accepted UI design, currently effective project UI decision, superseded and unresolved. These are **semantic standings, not a mandatory state machine**.

Project Product, accepted UX interaction/navigation/IA/state meaning, reusable Design Standards, security/privacy/accessibility constraints and specific content/asset authority remain effective **at their own original sources**. A UI author cannot silently revise them by presenting a persuasive mock.

| Question | Legitimate owning responsibility |
| --- | --- |
| Actor/domain meaning, legal/privacy/business effects, accepted success/unknown | Target-project **Product** |
| UX Flow, IA, navigation/page paths, interaction/state behavior | Target-project **UX** |
| Bounded visual expression, content treatment, screen variants, UI component candidates | Authorized **UI/Design** decision owner |
| Reusable cross-feature brand/visual patterns, components/tokens, copy/asset standard promotion | Target-project **Project Design Standards** owner |
| API, authorization implementation, DOM/CSS/framework, backend/data integration, rendered production test | Authorized **Engineering** owner |

A feature-specific component design may be accepted **for that feature** without becoming an approved reusable project standard. An existing canonical project-standard rule constrains the feature UI within its applicability. Design evidence/reference images can have approved **direction standing** without becoming pixel specs or production assets.

## 2. Consumer input sufficiency before material UI acceptance

UI must inspect actual effective Product/UX/Standard sources relevant to the intended decision; a convenient handoff summary cannot substitute for source standing. The local [13-input definition](definition.md#2-input--13-decision-specific-information-needs) and [UI Input Sufficiency Check](definition.md#3-ui-input-sufficiency-check) express the reusable classification.

In **new/material experience work**, default UX coverage includes an accepted/legitimately sufficient **O2 flow diagram** and **O6 representative Lo-Fi structural screens**, plus applicable UX O1/O3/O4/O7 and web O5. Accepted original equivalents can satisfy without producing new files. An exception must name **O-ID, affected scope, actual evidence, legitimate owner/delegation and consequence for the UI consumer**. A missing UX decision cannot be replaced with UI speculation, a pretty prototype, or a silent new page route.

If a material source is absent or conflicting, record the **exact affected UI decision and owning gap**. Independent, safe, authorized visual exploration may continue with `PROPOSED` standing; binding UI acceptance/implementation use of that decision must not be claimed. A technical feasibility finding can motivate a UX/UI reconciliation proposal; it does not transfer authority over page routing or Product truth to Engineering.

## 3. Human UI review and exact-revision acceptance

For a material new/changed UI decision, identify:

1. **Decision and scope:** affected actors, surfaces/screens, visual/interaction states, responsive contexts and out-of-scope behaviors.
2. **Authoritative inputs:** current project Product/UX/Design Standards, actual accepted revisions and applicable constraints; explicitly state proposed assumptions/gaps.
3. **Reviewable evidence:** exact UI candidate/artifact revision, actual screen/viewport/state coverage, source versus **performed rendered** evidence, asset provenance, representative copy and accessibility/testing limitations.
4. **Trade-offs and material approval:** what the Human truly accepted/rejected/deferred, permitted design freedoms, affected consumers and owner of unresolved or conflicting rules.
5. **Persistence:** record accepted source and decision separately when necessary to preserve **exact approved bytes**. Do not edit a previously reviewed prototype or accepted asset only to insert its own SHA/status and then assume old approval extends to new bytes.

Routine reversible tweaks within a legitimately delegated existing design system need no independent Human ceremony. Novel brand-defining expressions, material new UI precedents, shared standard changes and consequential Product/UX deviations require the applicable legitimate owner decision.

**An accepted UI render/prototype is a scoped Design decision**, not Product policy, a new UX flow, actual usability test, production implementation, verified runtime, asset license, project-wide standard promotion or release approval.

## 4. Minimum sufficient downstream UI handoff

For the **actual receiving decision**, make source references and this information discoverable; a compact index/record may suffice, not a mandatory packet:

| Consumer responsibility | Applicable UI information to consume |
| --- | --- |
| **Engineering Implementation** | Exact accepted material screen/state/responsive/copy/style/asset source; original Product/UX/standard constraints; freedom for DOM/CSS/components/framework; known blockers and actual design verification evidence |
| **Engineering Solution Design** | Material visual/interaction constraints, page-vs-state truth, effect/unknown expression and accessibility implications where technical decisions depend on them |
| **Visual/Accessibility Verification** | Claimed design visual outcomes, approved state/responsive examples, screen/viewport coverage, actual rendered checks and unverified accessibility claims |
| **Reusable Project Design Standard Evolution** | Proposed generalizable UI pattern, repeated-use justification, candidate variants/assets, affected source revisions and **separate** legitimate project-standard owner decision |
| **UI Reconciliation and Further Iteration** | New technical/UX/Product evidence, exact affected decisions, ownership, compatibility impact and what is safe to explore separately |

**Minimum discoverable fields:** project/scope/actor; intended consumer question; original effective Product/UX/standard refs with exact revisions; UI candidate/accepted artifact path and exact inspected bytes; major screen/state/responsive/copy/assets coverage; approved visual decisions and delegated implementation freedoms; actual render/accessibility/prototype check standing; unresolved gaps/owners; legitimate Human decision reference. Do not hide consequential rules in mock JS or an image.

**No mandatory named producer/consumer Space or physical output filename.** The consumer rechecks relevant original project authority. A handoff may link multiple existing accepted sources without copying them into a rival canonical spec.

## 5. Consumer compatibility and evidence discipline

**Generic fit:** If an actually declared reusable Input Contract applies to the known consumer, check its required information, source/approval standing, scope and exact revision; otherwise report `NOT APPLICABLE`. No invented future consumer or implied phase certification.

**Project-specific fit:** Check real target-project Product/UX/Design/SOP/security/asset/license constraints, authorized actions and acceptance needs independently of generic completeness. Report `SUFFICIENT`, `CONDITIONAL`, `BLOCKED`, `NOT CHECKED` or `UNVERIFIED` for the actual claim. A source-level check, responsive CSS presence or synthetic HTML prototype is not proof of rendered layout or independent accessibility/user test.

A new material Product fact returns to Product, UX navigation/IA/state to UX, reusable design rule to Project Standard, and Engineering feasibility/contract to Engineering. UI may propose a scoped choice only within its legitimate delegation. Do not reopen an accepted design solely for stylistic preference; revisit with material new evidence, approved scope change or actual consumer incompatibility.

## 6. Completion and nonclaims

UI design is sufficiently reviewable for the **bounded decision** when relevant accepted source meaning, visual proof/state/responsive/copy/asset treatment, Human standing, exact revisions, actual evidence and material gaps are discoverable from the target project **without chat memory**. When material visual inspection has not happened, disclose `NOT VISUALLY VERIFIED`; do not declare design visual acceptance based on source alone.

No UI approval automatically provides a reusable project-wide rule, component implementation, production CSS, protected-write authorization, real API effect, end-to-end integration evidence, usability certification or delivered actor outcome.

**Final rule: UI owns scoped expression, not the meaning it expresses or the reusable Design Standard that might later govern it.**
