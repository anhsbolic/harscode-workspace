# Project Design Standards — Authority, Evolution & Handoff

> **Standing:** A3 RESEARCH DRAFT / HUMAN CONTENT REVIEW PENDING (2026-11-04). This document explains reusable decision/authority distinctions; **only actual target-project sources and legitimate project/Human approval can establish a binding standard**.
> **Direct entry:** [README](README.md) · [Definition](definition.md) · [AGENTS](AGENTS.md).

## 1. One owning decision, actual project branch

First identify **the current target project and effective branch**, then the actual approved original for the design rule. An old branch, experimental mock, Harscode research source, artifact index, remembered conversation or code artifact cannot silently replace that source.

| Decision / information type | Real owner; not automatically transferred |
| --- | --- |
| Product actor, business/legal/privacy/financial truth and consequential statuses | Effective target-project **Product** |
| Bounded UX flows, IA, webpage routes/Lo-Fi and interaction outcomes | **Feature UX** authorized owners |
| Bounded feature screen composition/copy/states and visual candidate | **Feature UI** authorized owners |
| Reusable project-wide design judgment, visual/brand/pattern/asset/copy rule | Actual target-project **Project Design Standards** owning document and legitimate Design/Human authority |
| Production UI component contracts and framework/CSS/API/DOM/runtime proof | **Engineering** |

A UX interaction pattern can be reusable project-wide standard; a specific UX journey remains UX-owned. A generic visual token can be a project rule; the React component implementing it remains Engineering-owned. A feature-specific visual candidate cannot promote itself to reusable Design authority.

## 2. Standing and adoption are scope/revision-specific

| Standing | Meaning for consumption |
| --- | --- |
| **Canonical / effective** | Project-owned accepted reusable rule **for its actual branch and scope**, with legitimate decision evidence |
| **Approved for a bounded use** | Accepted within stated feature/asset/direction scope; not automatically applicable project-wide |
| **Working / proposed / exploratory** | Useful evidence or a candidate; **not** a binding new project-standard precedent |
| **Evidence / reference** | Visual studies, screenshot, code, research, old decisions; can support review without owning Product/UI/standard truth |
| **Superseded / archived** | Not current, although retained for history and reconstructability |
| **Unverified** | A specific proof step (render, usability, consumer behavior, license, etc.) was not performed or supported |

**An approval must identify its real subject.** Approval of an exact existing project revision does not approve a subsequent edit; a commit/push does not equal Human acceptance, branch merging, design correctness or operational promotion. When appending an exact revision/status to the content would alter its reviewed bytes, record approval **separately** and point to the immutable content.

## 3. Reconciliation and change scope

Before writing: find the smallest actual rule conflict, existing owning source and consumer consequence. Do not duplicate the same effective rule in two supposedly equal owning files.

- **Reuse or local feature work:** keep original standard unchanged, feature UI/UX accepted at its own scope.
- **Stale reference, old OPEN wording or ambiguous responsibility:** correct the outdated navigation/header/status **only**, link to the newer accepted owning rule, preserve the original historical decision and distinguish still-OPEN items.
- **Material new reusable rule:** require actual repeated-use need or consequential cross-feature gap, scoped candidate, legitimate owner/approval and proportionate proof. Changes to brand identity, trust/financial meaning, accessibility guarantees or widely shared assets/components deserve stronger consumer impact checks.
- **Supersession:** identify old effective scope and intended replacement, reconcile project routing and affected real consumers, preserve useful historical evidence; do not delete first and leave downstream agents with missing authority.
- **Target-project branch differences:** a pilot's canonical Design documents are **not automatically canonical on its `main`**. Make explicit adoption a separate authorized project decision when needed.

An authority map can be sufficient to clarify responsibilities but is **not** a new master Standards source. Copy/asset/interaction examples embedded in a different concern should explicitly reference their owner rather than become independent normative rules.

## 4. Human review and exact content evidence

Material decision review should identify: **what reusable rule changes, why existing coverage is insufficient, real owning project source/branch, who approves, original/effective revisions, actual supporting visual/user/evidence standing, relevant consumers/compatibility, reversal path and bounded acceptance scope**.

For routine delegated editorial reconciliation, retain a precise changed-path diff and source checks without manufacturing a new approval cycle. For first-time canonical rules, high-impact brand/meaning changes or broad supersession, obtain the legitimate Human approval before claiming it effective. No Harscode guidance authorizes a project write merely because a connector is available.

## 5. Downstream consumption without a fixed packet

A real target-project UX/UI/Engineering consumer should discover:

| Need | Existing project evidence to point to |
| --- | --- |
| Current applicable rule | Owning project path + exact effective revision/branch, decision scope and exceptions |
| Relationship to Product and feature design | Accepted original Product/UX/UI decisions, not copied into a rival standard |
| Changed/superseded content | What materially changed, old standing, replacement owner and affected real consumers |
| Evidence and quality limits | What visual/behavioral/accessibility/asset/consumer checks actually ran; explicitly `NOT CHECKED` where absent |
| Consumer freedom and remaining gaps | Allowed feature decisions/implementation choices, unresolved project owner questions and next necessary acceptance |

**No required handoff filename, project-standard artifact template, per-rule approval PDF, fixed I/P/O/O outputs, mandatory directory migration or new Space.** A revised original project source plus a clear router and bounded approval record may be sufficient.

## 6. Case evidence and nonclaims

[Kencleng source audit](../../experiments/org-01-reverse-lifecycle/a3-project-design-standards-kencleng-gap-matrix.md) shows an old Brand Brief's stale OPEN claims after Visual Guidelines resolved concrete choices, then a Human-approved pilot-only Design Authority Map/header clarification. The lessons are **source ownership, temporal coherence, branch-aware authority and minimal correction**. Its Sunlit palette, named fonts, trust rules, document inventory and ORG-01 UI states are **not** generic Harscode Design Standards.

A source-consistent project rule still needs actual downstream visual/runtime/usability/consumer proof where that proof matters. Neither a polished UI candidate nor a clean link check substitutes for it.

**Final rule:** the effective Project Design Standard lives in the **actual target project**, owned and changed by its legitimate authority—not in this reusable Harscode guidance.
