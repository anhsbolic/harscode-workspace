## Purpose and ownership

**Product selects and sustains legitimate value commitments, capability boundaries, consequential Product semantics and Product-level trade-offs.** It owns **what is worth promising, to whom, under which legitimate authority, and what must substantively be true**. Product does **not** default-own UX experience journey, flows/screens/navigation, implementation mechanisms, user research, technical security implementation or independent validation.

Distinguish **decision accountability, evidence/contribution from other concerns, and final Human/domain authorization**. Product cannot exceed binding privacy, legal, security or other institutional authority. Depth follows consequence, not document taxonomy.

## INPUT — five decision-specific information groups

| ID | Actual needed information and source |
| --- | --- |
| **I1 Value/problem evidence** | Desired benefit, intended beneficiaries, real/hypothesized demand, affected actors, trade-off and evidence; actual Human/domain priorities |
| **I2 Legitimate actor/domain context** | Material Domain Roles/relationships/eligibility, authority, data/consent/privacy, rights, obligations and lifecycle effects from owning project/domain sources |
| **I3 Existing Product commitments** | Current approved project rules, scope/exclusions, source precedence, accepted behavior and relevant code as evidence (not automatically Product authority) |
| **I4 Other-concern evidence** | UX actor/context findings, Engineering feasibility/risks and standards/security/privacy constraints when relevant, with original ownership retained |
| **I5 Decision standing and uncertainty** | Actual approvals/owners/delegations, hypotheses, unknowns, observational and verification limits, contradictory sources and consumer questions |

These are **information needs**, not mandatory input files, ordered phases or named Spaces.

## PROCESS — six iterative Product responsibilities

| ID | Responsibility |
| --- | --- |
| **P1 Value and priority selection** | Challenge problem/value evidence and consequential trade-offs; choose legitimate opportunity and beneficiary |
| **P2 Capability commitments** | Decide promised capability, exclusions and Product outcomes without preordaining UX/technical representation |
| **P3 Consequential meaning** | Resolve material Domain Roles, rights, data purposes, eligibility, business invariants, success/denied/partial/unknown effects and domain lifecycle changes |
| **P4 Decision-specific sufficiency** | State observable SC/REQ/AC **or equivalents when material**; inspect negative cases, contradictions, downstream semantic ambiguity and affected parties |
| **P5 Legitimate decision/approval** | Separate delegated routine decisions from material Human/domain authorization; preserve accepted scope and exact original revision |
| **P6 Reconciliation** | Challenge and respond to UX/Engineering/UI observations, real usage and risks; amend only Product-owned meaning under actual authority |

No mandatory waterfall, Product User Journey, PRD, outcome tree, or six-documents requirement.

## OUTPUT — four logical meaning groups, not four mandatory files

| ID | Meaning a consumer must find when needed |
| --- | --- |
| **O1 Value intent** | Selected problem/value, intended beneficiaries, bounded objective, priority, relevant success signal and evidence confidence |
| **O2 Legitimate Product commitments** | Actual capability/exclusions, rights/eligibility/Domain Role changes, material business invariants, required data/disclosures, outcome/failure/unknown semantics and observable acceptance obligations |
| **O3 Authority & constraints** | Owner/delegation/approval and scope, legitimate governing project source/revision, legal/privacy/security constraints and authoritative precedence |
| **O4 Uncertainty & evidence status** | Settled vs proposed, observed vs inferred/hypothesized, unknowns, impacted binding decisions, owner, evidence quality, unverified runtime claims |

An **approved Product Contract**, if a project uses that form, must be **self-contained for its binding rules**. Other owning sources and a durable reference index may satisfy these logical outputs; a pointer cannot hide missing normative semantics. A Product-authored meaningful *domain lifecycle* is appropriate if rights/consequences change through time. **Actor experience journey, UX Flow, IA, web routes and Lo-Fi belong to UX**, not universally Product.

## OUTCOME — six desired, not pre-verified properties

| Quality | Defensible evidence target |
| --- | --- |
| **Legitimate** | Decisions within real authority, legal/privacy/security and affected-actor rights |
| **Valuable** | Reasoned desired value and real evidence proportional to the consequential decision |
| **Coherent** | No conflicting Product promises, permissions, status/invariants or affected-party consequences |
| **Sufficient** | Actual UI/UX/Engineering consumer does not need to invent material Product semantics |
| **Reconstructable** | Fresh reader sees original exact source, owner, approval, scope and unresolved limits without chat memory |
| **Falsifiable** | Observable acceptance and negative/unknown semantics as necessary; planned checks are not performed tests |

## Direct consumer information and boundaries

- **UX** consumes O1–O4 as applicable, then investigates real actor needs and designs experience independently. Product cannot dictate journey/screens merely to fill its output.
- **UI** consumes accepted original Product meaning directly for consequential fields/disclosure, rights and success/unknown truth, plus independently owned UX/Design authority.
- **Engineering** consumes accepted invariants, roles/rights, acceptance, unknown and security constraints, and owns proposed technical mechanisms and separate verification.
- **UX/UI/Engineering feedback → Product** is evidence and a scoped question, never automatic Product policy change.

**Sufficiency is decision-specific:** a reversible experiment may proceed with clearly labeled hypotheses; a consequential binding claim cannot silently substitute a Product answer for an unresolved owner decision. Hold affected edges only. Exact project Product authority and Human approval must be discoverable; Harscode research cannot grant them.
