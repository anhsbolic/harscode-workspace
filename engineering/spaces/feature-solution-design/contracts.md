> **Status:** RESEARCH PROPOSAL / NOT FORMED. This is not the immutable historically approved S1 I/O contract.
> **Owner:** Reconstructed Engineering Space proposal; concrete project inputs/outputs belong to their owners.

## Required input classes

| ID | Meaning |
| --- | --- |
| **I1** | Approved bounded product/technical objective, behaviors, acceptance and owning source revisions; binding versus evidence explicit |
| **I2** | Current Design, architecture, security and implementation constraints, source precedence and protected-path policy |
| **I3** | Exact project repository/ref/SHA, relevant active code/contracts, read access and environment facts |
| **I4** | **Human-direct** assignment: bounded design responsibility, downstream consumers, output/state paths, permitted tools/writes, mode and consequential Human gates |

Missing or contradictory material authority, inaccessible code, incompatible consumer expectation or unauthorized write scope means REFUSE/BLOCK the affected action. Engineering design freedom is not by itself missing Product Authority.

## Required outputs (logical coverage)

| ID | Result |
| --- | --- |
| **O1** | Shared material solution decisions, rationale, ownership and meaningful cross-boundary trade-offs |
| **O2** | Producer/consumer interface, data, authorization, persistence, state, result/error and invariant contracts |

| **O4** | Verification obligations traced to acceptance, including risk, security and relevant negative paths |
| **O5** | Original source revision → decisions/output trace, independent review findings and limits, revisioned handoff, Human approval standing and consumers |

Coverage is compulsory when applicable; a five-file bundle is **not** required. A future consumer may require an independently addressable typed API contract; formal OpenAPI/spec edits need separate project authorization. An API shape cannot be invented as an approved project contract.

## Internal responsibility and evidence

Requirements/authority inspection, solution architecture, experience alignment and critical solution review are candidate responsibilities. Actual Specialist identity, number and harness isolation are **unproven**. A Reviewer must have original sources and sufficient independent context, not just a producer summary; a self-check must not claim independent assurance.

Minimum runtime demands remain: **R1** source fidelity, **R2** bounded artifact writes, **R3** scoped Specialist context/knowledge, **R4** reviewer independence, **R5** versioned handoffs, **R6** enforceable revision-bound Human gates, **R7** truthful executed evidence, **R8** observable Human-direct coordination. Actual readiness is NOT VERIFIED by this document; the [historical definition](../../../deprecated/legacy/spaces/feature-solution-design/composition/execution-requirements.md) is reference evidence, not an effective replacement contract.

Human formation approval is separate from Human-direct invocation. Conditional Human gates stop unresolved owner product decisions and protected/security scope changes. Final Human acceptance of the **exact output revision** is separate from Space completion. Default supervised; autonomous requires explicit separate Human authorization and still obeys hard gates.

## Result standing

Production result `COMPLETE / PARTIAL / BLOCKED / FAILED` is distinct from item standing `APPROVED SOURCE / DELEGATED / PROPOSED / UNRESOLVED`, Human acceptance, and evidence scope (`DESIGN REVIEWED` does not mean `RUNTIME VERIFIED`). No untested output is called implementation-ready if a consumer-critical invariant or contract is unresolved.
