# Experience Specialist — Experience Contract Reference

> **Type:** Agent-owned applied knowledge, **not** universal UX policy or a replacement for Product/Design authority. Read the project's current accepted experience principles, design system, content/accessibility standards and research findings first. **Project-owned effective standards prevail over local examples**, even when the interaction style differs. Escalate conflict with approved Product outcome, user safety, accessibility or binding security obligations to its owner. See [Space-wide project precedence](../../../../space-formation.md#project-standards-take-precedence-over-space-base-knowledge).

## Which layer owns what?

| Layer | Owns | Space Agent must not assume |
| --- | --- | --- |
| Product authority | Actor goals, meaning of outcomes, accepted behavioral constraints and scope | A solution can invent eligibility, recovery promises, acceptance or business policy |
| Design authority | Approved interaction/visual/content principles and user experience expression | Technical preference automatically overrides an accepted Design rule |
| Experience solution (O3) | Implementation-consumable actor action/state/result meaning connected to actual O1/O2 system contracts | O3 approves new Product/Design direction or serves as pixel-perfect UI design |
| Implementation owner | UI components, framework behavior and rendered quality within accepted contracts | A proposed journey is tested merely because it is documented |

## Trace consequential interaction meaning

For each applicable step or state, capture: **actor intent → permission/precondition → action → system authoritative effect/state → what can be truthfully shown → next safe action/inspection**. Select only states needed by the real assignment; for a high-impact mutation consider pending, timeout/unknown outcome, denied, failure, partial, known conflict, retry/replay and later inspection as *conditional* checks.

- Success must correspond to the domain-authoritative condition, not an optimistic UI state, request dispatch or transient notification.
- If the system cannot know the result yet, communicate uncertainty and an evidence-based path to check it; do not falsely turn it into failed/succeeded.
- Preserve source provenance. An actor-entered assertion, externally imported datum, internally reviewed datum and independently verified claim can have different standing; **never imply stronger trust than evidence supports**.
- For consequential actions, honor approved pre-effect disclosure and confirmation boundaries where applicable; do not prescribe modals, step count, checkbox patterns or recovery journeys without a source need.
- Authorization is enforced by trusted components, not by hiding a button. O3 must align with O2 resource/identity/error and data ownership contracts.
- Account for keyboard, assistive technology, text alternatives, focus and responsive behavior to the extent required by project standards; rendered accessibility needs actual evidence at its implementation boundary.

## Reconcile with architecture and project standards

For every material user-visible state name the O2 system owner and supported response/error or event. If a Design-required user action has no true server/data contract, return a specific O2 gap to the Architect; do not invent an API operation. A custom UI pattern is not justified only because it is elegant—follow existing project components and accepted design conventions unless the Design owner authorizes a change.
