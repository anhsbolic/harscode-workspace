# Rancang — Artifact Guidance and Consumer Representation

> **Standing:** Optional artifact guidance in FR-01–FR-04 research candidate (**NOT FORMATION APPROVED**); no mandatory layout, separate approval or runtime claim. Approved baseline: `47297c6f369dad4d4e4c4f90f0e81eb0310be7cf`.
> **Owner:** [Rancang External Contract](../contracts.md).

## Representation and precedence

Use current **effective** target-project Engineering/Design documentation and interface representation standards first, including applicable project-owned language/terminology conventions. Project-specific writing policies are not Harscode configuration; [optional writing reference](../../../references/project-language-writing-example.md) is non-binding and never requires every artifact to be bilingual. When a material Engineering Standard needs creation/revision, follow the bounded Architect proposal → independent assessment → exact Human approval → authorized project-owned persistence path in the external contract. A Space-local template is not binding project policy.

Choose the minimum representation that allows actual consumers to use and verify the design. One named section/anchor can satisfy several logical outputs; a separate machine-readable proposed API schema is needed only where actual consumer requirements justify it. Do not edit the project's canonical feature API/OpenAPI/specification as part of Rancang O2.

## Effective output and evidence lifecycle

At completion, expose **one discoverable effective output set per assignment**. Consumers should not need to reconstruct binding X1/O1–O4 meaning by merging conflicting historical revisions; carry applicable obligations forward with owner/source attribution. Preserve historical identities and supersession through reconstructable immutable project evidence (for example pinned Git commits), not competing current editable contracts. **No flat-root or revision-folder layout is imposed**: physical organization belongs to the project.

Separate **durable deliverables** (current contract, source/output provenance, independent findings, handoff, sufficient verification summary and acceptance standing) from **temporary working machinery** (one-off validation scripts, parsed/dereferenced views, generated smoke/types and verbose reports). Retain machinery only when actual consumer, replay/assurance or project-tooling needs justify its cost. Otherwise clean it **after checks/reviews**, keeping actual input revision, method/commands and tool versions, observed results, limitations and historical reconstruction references; do not claim ephemeral bytes were archived if they were not.

Authorized administrative repackaging after exact Human acceptance must preserve accepted substance and distinguish **original accepted identity** from **new packaging hashes/standing**. A material semantic delta needs affected owner/review/Human decision, not inherited approval. Reconcile effective links, manifests and navigation; do not delete still-needed project-owned decisions/follow-up records merely because they sit beside superseded drafts.

## Minimum artifact evidence

Each materially consumable section/payload needs:

| Fact | Required meaning |
| --- | --- |
| **Identity / producer** | Stable anchor/type and named accountable Agent |
| **Effective sources** | Accepted work input/standing, applicable standard revisions, project technical baseline where material |
| **Proposed result** | Exact design decision/interface/experience/verification obligation with proposal vs accepted authority clearly separated |
| **Revision** | Exact produced artifact/section revision and dependent revisions |
| **Assessment** | Actual independent Security and Solution Reviewer findings/limitations, when applicable; executed vs NOT RUN evidence |
| **Consumer standing** | Intended consumers, project-bound compatibility and material blockers/unresolved decisions |

No mandatory metadata file, universal diagram count, copied Product Contract or new registry.

## Human-facing decision summary (within the existing handoff)

Start the Coordinator's handoff with a **concise decision summary**: accepted outcome; material solution choices and why they satisfy the requirement with justified effort; consequential experience, feasibility and security trade-offs; remaining risks/evidence limits; and any exact Human decision needed. Link each substantive assertion to its owning revision. A manifest of hashes is necessary for traceability but not sufficient for a decision-facing handoff. Do not create a second canonical solution document, require a fixed table, or duplicate all O1/O2/O3 content.

## Consumer entrypoints (within the existing handoff)

For each **known intended** consumer, point from the exact bundle to the *relevant owning artifacts/sections*, source authority and revisions; show whether the bundle is only proposed or Human-accepted, which consumer compatibility checks were actually performed, outstanding format/spec adoption and authorization requirements, and the **next permitted action**. A backend consumer may need O1/O2, backend-relevant O3/O4 and Security Findings; a frontend consumer may need O3, O2, relevant O4 and Design authority. These are **illustrative slices**, not fixed per-Space input contracts or new mandatory files.

Make the bundle locatable from target-project-owned durable work/assignment references. Downstream must reopen effective project authority and inspect exact producer content; the handoff is a pointer, **not a substitute contract**. An unknown future consumer is not pre-certified; its actual declared Input Contract and project-bound requirements are assessed when the consumer exists. Do not equate Rancang COMPLETE, exact Human acceptance, formal API adoption and permission to implement.

## Revisioned Engineering Solution Handoff

Coordinator returns one index/payload containing the **Engineering Obligation Map (X1)**, applicable **Solution Decisions (O1)**, **Technical Contracts (O2)**, **Experience Contract (O3)**, **Verification Obligations (O4)**, plus **independent Security Findings and Solution Review and Human-facing bundle metadata (O5)**.

Keep Security Findings and Solution Review independently owned even when packaged or linked from one document. Reference any authorized Engineering Standards revision by its **owning project source and effective revision**, distinct from a proposed-but-not-effective update.

Rancang production COMPLETE requires fulfilled applicable obligations and required independent review **without unresolved material findings that defeat binding obligations or consumer-critical contracts**. Non-blocking limits must remain visible; merely recording a blocking finding never satisfies completion. Human acceptance of exact bundle, canonical feature contract adoption, implementation and runtime verification are separate downstream concerns.
