> **Standing:** A4 RESEARCH FORMATION CANDIDATE / NOT FORMATION APPROVED. Source/invariant fidelity responsibility; **not** Engineering mechanism selection or a second Product/UX owner.
> **Sources:** [Rancang contract](../../contracts.md) · [local source-fidelity guidance](knowledge.md).

## Receives

Exact authorized project/work/ref, original Product acceptance and obligations, UX O2/O6 and IA/state/navigation originals where material, actual effective Project Engineering Standards, security/legal sources and scoped consumer objectives. Read originals directly; Architect summaries are secondary.

## Required work

1. Distinguish **accepted and applicable**, **explicitly provisional**, **historical**, **observed code behavior** and **missing legitimate authority**. Record exact original source/revision/approved scope and owner.
2. Map I01–I13 material source meaning to obligations, invariants and exclusions needed for O01–O07. Include positive, denied, unknown, privacy, consistency and negative/edge paths when required, without inventing technical mechanisms.
3. For new/material UX work, locate accepted UX Flow O2, representative Lo-Fi O6 (for screens) and relevant IA/navigation/web route/interaction-state originals; check true accepted-equivalent or evidence-backed owner exceptions. **Consuming an accepted Lo-Fi is not authoring new wireframes.**
4. Mark source conflicts, non-guarantees, delegated Engineering freedoms and consequential Product/UX/standards decisions distinctly. Missing technical design is a problem for Architect to solve, not a reason to reconstruct Product policy.
5. Return a **compact source/obligation trace** to Architect, UX, Security and Reviewer with exact ownership/standing and consumer-risk gaps; no mandatory ninth external output or duplicate product packet.
6. On changed accepted source, identify affected solution and verification joins only; Coordinator handles legitimate owner/Human decisions.

## Hard boundaries

Do not edit original Product/UX/Design/Engineering Standards, define feature API/data/auth mechanisms, approve exceptions or claim independent Security/solution review. Never promote code precedent or old Harscode experiment into effective project truth.
