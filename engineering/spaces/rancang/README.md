## Mission

Turn an authorized bounded objective and sufficient accepted Product, UX and Engineering Standards/technical evidence into **one coherent, implementation-consumable Engineering Solution**. Make architecture, identity/authorization, API, data, state/recovery, security design and technical verification compatible for *actual intended implementers*, not merely well formatted. Aim for **Feasible, Secure, Consistent, Reliable, Implementable and Verifiable** design; actual runtime outcomes remain separately unverified.

The [External I/P/O/O Contract](contracts.md) states **13 logical inputs, 10 iterative processes, 8 logical outputs, 6 desired outcomes**. These do not dictate a fixed document count, lifecycle engine, order of work, or one-to-one phase/Space/Agent mapping.

## Authority, boundaries and responsibilities

- Product owns consequential domain/actor rules; UX owns flow, IA, webpage routes/Lo-Fi/interaction states; UI owns visual expression. Rancang can challenge technical feasibility and propose alternatives, **not silently choose different Product/UX meaning**.
- [Engineering Project Standards](../../project-standard/README.md) is a separate direct concern. Rancang **consumes** effective standards and reports a material standards gap, not a default standards-writing or governance capability.
- Rancang owns proposed technical API paths/contracts, authorization mechanisms, data/persistence/transaction decisions, technical failure semantics and implementable security controls; canonical feature API/schema adoption, actual code/migrations, frontend rendering, deployment and final integrated acceptance are downstream authorities.
- Hi-Fi is **not** a mandatory/default input or media-processing prerequisite. Accepted UX Flow/Lo-Fi and relevant interaction requirements are default material Design inputs with evidence-backed exceptions.
- Security and UX/Experience perspectives challenge Architect **early, from separately owned knowledge/original sources**, not just after implementation choices are fixed. Feasibility does not redefine their binding constraints.
- A small local task may use a simpler authorized Engineering path. A real project may use multiple implementation consumers; Rancang is not a full-stack Builder.

## Defined responsibility and knowledge boundaries

1. [Space Coordinator](agents/space-coordinator/agent.md) — authorized assignment, source/version joins, gates, durable state and O08 handoff.
2. [Requirements & Authority Analyst](agents/requirements-authority-analyst/agent.md) — independent original-source obligation fidelity.
3. [Engineering Solution Architect](agents/solution-architect/agent.md) — single accountable substantive technical producer of applicable O01–O07.
4. [UX / Experience Integrity Specialist](agents/ux-experience-specialist/agent.md) — distinct Design-origin constraints and truthful actor/consumer experience challenge, not an API owner.
5. [Independent Security Analyst](agents/security-analyst/agent.md) — independently grounded threat/security assessment and independently owned findings, not a feasibility-driven self-review.
6. [Independent Solution Reviewer](agents/solution-reviewer/agent.md) — independent end-to-end solution coherence, implementability and source/assurance review.

These are six **semantic responsibilities**, not proof of six native independent Agent sessions or a demand to invoke all six for trivial tasks. Required independent assurance cannot be producer self-approval or shared-context roleplay. Actual role separation/tool isolation is a Harness/runtime evidence question.
