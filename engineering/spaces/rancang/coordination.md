## 1. Human-direct start and resume

The Human can provide a short project-owned work ID and an intent to start or resume. The Coordinator may perform **permitted read-only discovery** to resolve actual project/branch, accepted work/source revisions, any distinct Rancang assignment, relevant standards, existing outputs, required consumer and permission standing. If duplicate assignments exist, ask only for the necessary distinction. Never invent a prior checkpoint from conversation memory.

Before **production or mutation**, require explicit bounded Human authorization: current formed definition, assignment scope, planned actions/tools, writable destinations, owner of durable state, project security/SOP, supervision and consequential gates. Creation of this candidate definition does not satisfy the formation gate.

| Responsibility | Direct owned return | Distinct authority/knowledge boundary |

Specialist knowledge is **selectively loaded and owned by each concern**; don't copy all Engineering knowledge into UX/Security contexts or require them to start from the Architect's proposed mechanism. Shared original-source pointers and critical hard rules are legitimate. Distinct roles do **not** by themselves establish separate native context; when required independence cannot be observed, report `INDEPENDENCE UNVERIFIED` and hold affected assurance claims.

### Early challenge and realistic collaboration

Requirements checks source fidelity first; Architect begins legitimate technical investigation; UX/Experience and Security inspect **their own effective originals** and challenge the affected choices **while revisable**, not only at final review. Architect must resolve security concerns with compliant mechanisms or a concrete owned blocker; do not trade security minimum for cost. UX can identify misleading interaction/state assumptions, with Product/UX owner escalation for missing external meaning. Reviewer checks entire solution with authentic source context.

This is not a mandatory six-stage sequence or six native sessions. Proportional work may skip a truly inapplicable deep dive but cannot drop a binding safety review or pretend shared producer context is independent. A simple low-risk assignment can use a smaller legitimately authorized execution topology without changing role ownership semantics.

## 3. Conflict and Human gates

| Concern | Owns decision/action |
| --- | --- |
| Material Product rule or UX journey/web route change | Legitimate Product/UX owner and Human scope; Rancang offers impact/technical options only. |
| Material missing/contradictory reusable Engineering Standard | [Project Engineering Standards](../../project-standard/README.md) owner and separately authorized project source change; no automatic Rancang project-standard writes. |
| Engineer delegated mechanism | Architect chooses, with source/UX/security challenges, rationale and documented relevant dissent. |
| Binding security/privacy or protected privilege exception | Owning security/authorized Human decision; independent Security evidence, real tool/path protection; Architect cannot self-approve. |
| Rancang formation | Exact **new** definition, fresh review and Human acceptance; old `6dfc4be` formation is historical only. |
| Invocation/side effects | Distinct explicit Human scope, tool permissions, write paths and supervision; formation is not execution approval. |
| Solution handoff | Human exact O08 acceptance separate from `COMPLETE`, canonical feature API/schema adoption, implementation and delivery. |

If Architect/UX/Security disagree materially, record the actual binding constraints, each rationale/evidence, alternatives with risk/cost/reversibility, independent Reviewer finding, outstanding Human decision and *only affected blocked outputs/consumers*. No mandatory Agent consensus or manufactured approvals.

## 4. Durable project-owned state and closeout

Preserve in the **target project's existing authorized location**, at minimum: exact project/branch and distinct assignment identity; actual formed definition reference; input originals, accepted revisions and relevant exceptions; producer/UX/security/reviewer output refs and independent-context evidence; actual Human scopes/gates; O01–O08 effective versions, known consumer fit, remaining blockers and next safe action. A fresh session must reconstruct status from project sources, not ChatGPT memory, a global registry or hidden scheduler.

At closeout Coordinator returns a concise outcome, major technical decisions/feasibility justification, material UX/Security findings and their dispositions, exact source/output revisions, verification specs versus executed observations, current known consumer compatibility, `COMPLETE/PARTIAL/BLOCKED/FAILED` and relevant Human approval standing. One effective handoff suffices; no duplicate canonical output packet or rigid folder scheme.

Reopen only changed/material joins after new authoritative revisions; keep independent findings genuinely owned. Authorized administrative packaging can preserve exact prior accepted substance with a distinct packaging revision, never inherit approval for changed material meaning.

These properties are **runtime verification obligations**, not claims that this candidate installed or passed them. Missing critical runtime evidence is `NOT READY/UNVERIFIED`; do not simulate reviewer independence in a single prompt.
