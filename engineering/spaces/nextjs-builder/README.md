## Mission and coherent external result

Transform an authorized, bounded frontend objective or defect into an actual, inspectable **Revisioned Next.js Frontend Implementation**, preserving effective project Product/Design/Engineering/security meaning, producing intentional and usable experiences, and truthfully reporting observed verification, consumer readiness, and remaining limitations. The deliverable is software and attributable evidence, not merely a plan or mockup.

**Primary Outcome (approved working wording):** Produce runnable Next.js frontend implementation of authorized behaviors and experiences, with sufficient verification evidence against applicable contracts and risks, inspectable through source, actual application behavior where observed, and executed evidence—not completion claims alone.

The capability is **project-neutral but Next.js-specific**. It does not require a Product Outcome, PRD, Rancang, OpenAPI, Figma, sitemap, or a particular file format on every assignment. A project-authorized bug, accessibility fix, UI feature, visual refinement, performance remediation, technical refactor, or prototype translation can qualify when its **meaning and standing** meet the Input Contract. ORG-01 is a validation consumer, not reusable policy.

**Demand:** Next.js implementation needs coordinated technical correctness and visual/content craft, early two-way Engineering–Craft reconciliation, and truthful verification of frontend/state/API behavior. A distinct capability is justified by these consumer-facing production risks; avoid forcing it on tiny work where a simpler permitted path suffices.

## Explicit API execution mode

For API-dependent work, the **default is `MOCK_DEVELOPMENT`**, unless Human expressly selects `REAL_API_INTEGRATION`. The mode belongs to an exact authorized assignment. Backend readiness, a message that the API is available, or a finished mock frontend **never automatically switches mode**.

- **`MOCK_DEVELOPMENT`:** implement against an effective/accepted implementation-consumable contract using contract-faithful mocks, when permitted by the project; backend runtime is not a prerequisite. Do not invent missing domain/API semantics, treat mock success as backend evidence, or include a hidden production mock branch. If a material interface contract is absent, perform only genuinely independent authorized work and report the blocked edge.
- **`REAL_API_INTEGRATION`:** explicit Human selection; verify actual backend contract/runtime/readiness and perform frontend-side integration within scoped permission. If backend API is unavailable, contradicts the effective contract, or has an unresolved material integration blocker, perform bounded diagnosis, report accountable owner/evidence, and **stop the affected integration assignment—never fall back to mock development**. Existing permitted isolated test doubles do not count as real integration or a mode switch.
- **API-independent work:** mode not applicable; do not create mocks ritualistically.

Parallel mock frontend and backend assignments can finish separately. A later real-integration assignment is **new Human authorization or explicit authorized re-scope**, not automatic continuation. See [external contract](contracts.md).

## Defined responsibilities

The exact Human-approved formation defines four roles; this is **not** proof of four native independent runtime sessions:

1. [Space Coordinator](agents/space-coordinator/agent.md) — external input/output, mode/authorization, producer joins, Human gates and O4 handoff.
2. [Next.js Engineer](agents/nextjs-engineer/agent.md) — single accountable O1/O2 implementation owner, relevant executed checks and corrections.
3. [Experience & Craft Specialist](agents/experience-craft-specialist/agent.md) — early material UX/visual/content/asset guidance and actual rendered craft findings; not Design authority or second implementation owner.
4. [Independent Frontend Reviewer](agents/independent-frontend-reviewer/agent.md) — independent source/implementation/evidence assessment when required; no self-approval.

For material UI, Engineer and Craft collaborate **early and bidirectionally**, without mandated order or a Design-first phase. Participation and assurance scale with work and risk; a defined role is not a mandatory separate native session for every small change. Independence must be observed, not inferred from a role label. Frontend security knowledge belongs to Engineer and Reviewer, with specialist escalation when necessary; no permanent fifth Security Agent.
