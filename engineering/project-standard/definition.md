# Engineering Project Standards — Semantic Contract

> **Standing:** A4 RESEARCH DRAFT / HUMAN CONTENT REVIEW PENDING. Not an exact approved target-project standard, mandatory inventory, autonomous governance Agent or formed production Space.
> **Basis:** [A4 Zero-Based Rancang Target Design v1](../../experiments/org-01-reverse-lifecycle/a4-rancang-zero-based-target-design-v1.md), research-approved experimental Engineering Standards input and [Engineering Space formation discipline](../space-formation.md).

## 1. Purpose

Enable a project to discover, verify, reuse, create, revise or retire **reusable Engineering rules** only when doing so helps actual committed work. Ensure clear owning authority, scope, exact effective revision, consumer fit, exceptions, security constraints and change impact. The concern is **project-agnostic guidance**: it never stores the project's authoritative standards itself.

## 2. INPUT — decision-relevant information

| Information | Real source / applicability |
| --- | --- |
| Triggering technical question | A current/committed consumer needs a cross-feature/shared Engineering decision, or current rules conflict/stale/miss a material guarantee. |
| Effective current project technical authority | Approved standards, ADRs, architecture policies, accepted shared interface conventions, SOPs and actual scope/revisions; absent rules must be identified, not imagined. |
| Accepted Product/UX/Design meaning | Material Product invariants, relevant experience/navigation and accessibility constraints. A technical standard cannot silently override them. |
| Security/privacy/protection floor | Current binding security obligations, permissions, laws and trust/data boundaries, with independent expertise when consequential. |
| Actual technical evidence | Current repository/stack, provider/consumer constraints, existing canonical contracts, deployment/operational realities, NFRs and known evidence limits. |
| Change impact and Human authority | Affected features/consumers, migration/compatibility, risk/cost/reversibility, actual delegated owner and exact approval/write scope. |

No fixed documents or upstream Spaces are implied. **Engineering Standards & Technology Stack is required information when material**, not an obligation to generate an exhaustive catalog before every Rancang assignment.

## 3. PROCESS — responsibilities, not a sequential workflow

1. **Locate original and owner:** find the project branch, accepted rule, exact standing, intended scope and legitimate change authority.
2. **Classify real need:** reuse sufficient existing rule; make a delegated feature-level Engineering choice; reconcile inaccurate/stale source; or propose an actual shared-rule change based on observed repeated need **or justified cross-feature applicability**.
3. **Challenge the proposed rule:** verify Product/UX integrity, independent security floor, live code/consumer constraints, expected benefits, material downside, alternatives and the cost of governance.
4. **Determine correct scope:** narrow local choice vs project-wide rule; assess future compatibility, migration/rollback, exception handling and affected known consumers, without fabricating future users.
5. **Obtain real authority when necessary:** material new shared rule, breaking change, security-sensitive policy or supersession needs the legitimate project Human/owner decision on **exact text and scope**. A suggestion or commit is not acceptance.
6. **Persist and reconcile only if authorized:** edit the smallest owning project sources, recheck actual effective revisions, update genuinely affected references/consumers and label unverified evidence accurately.

No mandated process stages, registry, standards committee, agent count, scheduled checks or automatic writes. A valid result may be **REUSE / NO CHANGE** at step 2.

## 4. OUTPUT — decision outcomes

| Result | Minimum intelligible content |
| --- | --- |
| Reuse / no change | Effective project rule or justified absence, applicable scope and allowed Engineering discretion; no extra file. |
| Source/standing clarification | Correct owning rule/route and supersession ambiguity without silently changing approved substance. |
| Scoped candidate standard | Concrete cross-feature need, proposed smallest sufficient rule, owner, alternatives, evidence, security review need, compatibility/change impact; marked PROPOSED. |
| Accepted effective rule/change | Legitimate approval **and** actual permitted owning project artifact persistence, exact revision, effect/scope, replaced rules and consumer reconciliation. |
| Consumer handoff | Findable effective source, decision freedom, constraints, material gaps, affected exact consumers and evidence limits. |

These can coexist in existing project documents; no Harscode-specific mandatory file taxonomy, project `engineering/project-standard/` path, standards inventory or separate output package.

## 5. Desired outcomes and safeguards

A real contributor can identify and apply the **correct, sufficient, project-owned** rule without relying on chat memory or being forced into needless standardization. Shared technical decisions remain coherent across actual consumers and are changeable via legitimate authority, with safe handling of security/compatibility risk.

**Security is not a tradeable preference:** project policy cannot waive law, higher-priority privacy/security protections or protected-path constraints. An independent Security assessment is required where binding rules or material risk demand it; feasibility influences which safe method is selected, not the security floor.

**Completion claims:** effective project source and approval must be real; a proposal is not policy, code precedent is not automatically a rule, and source review is not runtime/security test proof.
